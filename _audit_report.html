二、P1 — 已撤銷（按設計非漏洞）

P1 會員付費門禁漏洞（原分析 — 現已撤銷）

位置：routes/bookings.js:324-335（會員級別檢查）

缺陷：門禁只檢查 membership_tier 同 family_head_id，完全唔檢查 subscription_status === 'active'。一個 tier='family' 但無 active subscription（過期/未付款/戶主退訂但 flag 未清）嘅會員，可以照約所有付費服務（針灸/內科/推拿/床位等）。

實機證據（throwaway :4567）：
• 真正 general 會員（tier=general，無 family link）約付費 S2 → 403 membership_required（門禁正常）
• testkid1（tier=family, famHead=41, subs=(none)）約 S2（開診日 2026-10-16）→ 通過門禁，預約成功（200 / overlap 409）
• testcustomer / testpremium（tier=family, subs=(none)）約 S2 → 同樣通過門禁（200）
→ 證明：flag 與付款狀態 desync 時，付費門禁形同虛設。

影響：模擬一年 —— 戶主退訂/信用卡失效/upgrade 中途失敗，只要子女或會員仲留低 family/premium tier flag，就可以無限免費約付費服務，直接 revenue leak，且難以察覺（預約紀錄正常）。正常路徑 detachAllChildren 會清 flag，但唔保證所有 desync 路徑都清到。

修改提議：新增統一 helper hasActivePaidMembership(user)：
① family 會員 → 查 subscriptions WHERE user_id IN (全家 member ids) AND tier='family' AND status='active'；
② premium 會員 → 查自身 tier='premium' AND status='active'；
③ 門禁改為 if (!hasActivePaidMembership && !guestMode && !svc.name.includes('初體驗')) return 403；
④ 前端 isServiceLocked 同步用同一判定，避免「睇到可以約、落單先 403」。
⚠️ 改前先確認 upgrade 流程會即時寫 active subscription，唔好誤封真正付款中嘅會員。

三、P2 — 應處理（中）

P2 HR 系統對非管理員檢視損壞（staff/doctor 開 HR 見 403）

位置：hr.html:857 / 869 / 876 直接 call /api/hr/today、/api/hr/employees、/api/hr/leaves/all，冇 role check。呢 3 個端點係 requireRole('admin')（routes/hr.js:874 / 1050 / 1370）。

實機證據（Puppeteer，staff 登入）：
hr / desktop 同 hr / mobile 都錄到 3 個 API 403 + 4 個 console error（3×「403 Forbidden」+ 1×「Error: 無權限執行此操作」）。即 dashboard / 員工名單 / 假期審批面板 load 失敗，彈錯誤 toast。

影響：HR 系統係你點名要審嘅重點。staff/doctor 嘅「管理」檢視實際壞咗（self-service 如 clock-in / my-status / my-leaves 正常）。admin 開 HR 則全部正常（實測 19 API 全 200）。

修改提議：hr.html 按 currentUser.role 決定 load 邏輯：
if (this.isAdmin) { loadToday(); loadRoster(); loadAllLeaves(); }
或後端對呢 3 個端點俾 staff 返自己相關 subset（唔好全日 403）。最穩陣係前端 hide admin 面板 + 唔 call admin 端點。

P2 帳戶連結搜尋外洩其他客人 PII（電話簿遍歷）

位置：routes/memberships.js:1101 GET /api/membership/account-links/search（只 requireAuth，無歸屬 scope）

實機證據：testcustomer 搜 ?q=9 → 返回 testkid1/testkid2/testfamily 嘅 id / username / name / phone / membership_tier（電話 9100 0004/5/6）。任何登入用戶逐 digit 搜就係一本完整客戶電話簿。

影響：私隱外洩（你問嘅「隱性安全問題」）。雖然要登入，但家庭連結功能令佢可以被濫用嚟 harvest 電話。

修改提議：① 只返自己 family/account network 內嘅成員；或 ② 唔返 phone 欄；或 ③ 加 rate limit + 最少 3 字先搜。建議 ①②③ 齊做。

四、P3 — 加固 / 小缺陷（低）

P3 公開主頁 call admin-only /api/api-settings → 403 + console error

位置：js/app.js:3203（公開客人主頁 fetch /api/api-settings，用途係讀 AI 諮詢 toggle）

實機證據（Puppeteer）：index / desktop 同 mobile 各錄到 1 個 console error = 403 Forbidden（/api/api-settings），apiFail=1。

影響：細 —— 公開頁 console 報錯 + AI toggle 唔反映 admin 設定。但公開頁 call admin secret 端點係唔應該。

修改提議：開 GET /api/public-settings（只含 AI toggle 等公開欄位，冇 auth）畀主頁用；或前端硬編 AI toggle 預設值。

P3 JWT 存 localStorage（非 httpOnly cookie）

位置：js/auth-fetch.js 注入 localStorage.jwtToken。一旦出 XSS，token 即洩，攻擊者可冒充該用戶。

修改提議：轉用 httpOnly + Secure + SameSite cookie（需將 fetch 攔截器由 Bearer 改為 cookie auth）；或至少縮短 JWT TTL + 加 refresh，降低洩漏窗口。

P3 生產 CSP 含 unsafe-eval + unsafe-inline

位置：server.js helmet CSP。Vue runtime 模板要用 new Function()（必須 unsafe-eval，否則 #app 唔 mount）；inline style 要 unsafe-inline。

修改提議：預編譯 Vue 模板（build step，移除 in-DOM 模板）→ 可執走 unsafe-eval；抽走 inline style 轉外部 CSS → 可執走 unsafe-inline。收緊 CSP 前必須先拆 in-DOM 模板（否則整頁空白）。

P3 密碼驗證保留 SHA-256 legacy 分支（弱於 bcrypt）

位置：config/db.js verifyPassword 有 SHA-256 兼容分支。

修改提議：登入成功若該用戶仍用 SHA-256 hash，立即用 bcrypt 重 hash 並更新 DB（upgrade-on-login），逐步淘汰弱 hash。

P3 /api/find-user-id 帳號枚舉端點

遺留枚舉端點（已 rate limit 30/15min）。攻擊者可借統一錯誤訊息確認帳號存在。

修改提議：移除或合併入 login（login 已用統一錯誤訊息），減少攻擊面。

  • IDOR：bookings / memberships / hr / users / medicalRecords 均有歸屬校驗（實測 R1/R6 → 403）。

十、優化建議（非缺陷）

  • 統一會員狀態判定：將「有冇 active 付費會籍」抽成單一 helper（前端後端共用），避免再出 flag/付款 desync。
  • 前端角色適配：所有 portal 按 currentUser.role 決定 load 咩、show 咩，減少「call 到 admin 端點先 403」。
  • 公開端點分層：主頁/客人用嘅公開設定（AI toggle、紅日等）獨立成 public 端點，唔好 call admin secret。
  • 錯誤監控：前端 console error（如 403）可接 Sentry/診所內部 log，早啲發現接駁斷裂。
  • 會員到期提醒：subscription 過期前 N 日 push/email 提醒，減少「過期但 flag 未清」嘅窗口。
  • CSP 收緊路線圖：Vue 模板預編譯 + inline style 外置 → 執走 unsafe-eval/unsafe-inline。
