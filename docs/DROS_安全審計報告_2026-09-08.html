2. 發現（Findings）

HighF1 — account-links 自助連結 = 免費 family 會籍升級，繞過付費閘門

DROS 透鏡：Declared ≠ Implemented（同一 function 自相矛盾）+ GBAI 治理邊界違反（社交關係圖被授予付費特權）。

聲稱（代碼註解，已驗證）：

// routes/memberships.js:840
// 與 family_links（家庭訂閱父→子）分開：account_links 係純關係圖，唔影響會員級別／保險。

實作（同一 function，已驗證）：

// :861-862  端點只要求 requireAuth（任何已登入用戶）
router.post('/account-links', requireAuth, async (req, res) => {

// :896-901  目標按 username 或 phone 解析，僅要求 role='customer'、非自己
if (targetUsername) target = await q1("... WHERE username=? COLLATE NOCASE", [...]);
else if (targetPhone) target = await q1("... WHERE phone=?", [...]);
if (target.role !== 'customer') return ...;
if (Number(target.id) === Number(fromId)) return ...;   // 只防連結自己

// :923-936  「一連即轉」：雙方自動升 family
if (owner && owner.role === 'customer' && owner.membership_tier !== 'family') {
  await run("UPDATE users SET membership_tier='family' WHERE id=?", [ownerId]);   // 928-930
}
if (target.role === 'customer' && target.membership_tier !== 'family') {
  await run("UPDATE users SET membership_tier='family' WHERE id=?", [target.id]);  // 933-935
}
await syncFamilyPlan(headId);   // 943 生成發票（但無向 caller 收費）

漏洞本質：① 任何已登入 general 客戶，只要帶 {targetUsername:<任意已知客戶>} 即可令自己同對方升 family；② family 係付費會籍，membership_required 閘門（bookings.js:317、memberships.js:1183-1184）規定 general 只可預約「初體驗」，升級後免費解鎖全部服務；③ 全程無 Stripe / 無職員確認；④ 利用面低，只需目標 username 或 phone（可經 F4 枚舉取得）。

為何係「隱性」：項目記憶原記載「account_links 唔影響等級/保險/訂閱」，與實際代碼直接矛盾；矛盾甚至寫喺相鄰代碼行（840 註解 vs 928-935 實作）。

修復：A）刪除 928-936 升級邏輯，令 account_links 真係只係關係圖；或 B）若產品真要「連結即升級」，加 requireRole('staff','admin') 或 Stripe 確認，並修正 840 行註解。補測試斷言「general 用戶自助 account-links 後 tier 維持 general」。

MediumF2 — 重設密碼驗證碼於非 production 經 DEV FALLBACK 回傳客戶端

DROS 透鏡：Anti-Stub 環境守衛不完整（條件含「SMTP 未配置」→ 即使 production 部署若漏設 EMAIL_PASS 亦觸發）。

// routes/auth.js:548-556  （/api/auth/send-reset-code 內）
const isDev = process.env.NODE_ENV !== 'production' || !process.env.EMAIL_PASS;
if (isDev) {
  console.warn(`[DEV FALLBACK] 驗證碼 ${verificationCode} 已生成...`);
  return res.json({ ok: true, ..., dev_fallback: true, verification_code: verificationCode });
}

當 NODE_ENV !== 'production' 或 !EMAIL_PASS 時，6 位重設碼寫入響應體。若 staging 用 NODE_ENV=development 或 production 漏設 EMAIL_PASS，即洩漏 → 攻擊者完成重設 → 帳戶接管。

修復：isDev 只應由 NODE_ENV 決定，唔應含 !EMAIL_PASS；縱使 DEV 模式，驗證碼亦只寫 server log，絕不回傳響應體。

LowF3 — AI 問診路由全公開，無認證

DROS 透鏡：能力混寫（本應登入後使用嘅能力對匿名開放）+ 治理不一致。

// routes/ai.js
module.exports = (db) => {                                  // :9  無 auth 依賴
router.get("/categories", (req,res)=>{...});             // :21 無 requireAuth
router.post("/start-consultation", aiWriteLimiter,...);  // :40 只得頻限
router.post("/submit-answer", aiWriteLimiter,...);        // :91 只得頻限
router.get("/get-recommendation", (req,res)=>{...});     // :188 無 requireAuth

風險低（規則式、唔寫 PII），但接 LLM 後有成本/濫用面；與「會員才能用 AI 推薦」假設不一致。建議加 optionalAuth 並於文檔聲明公開性。

LowF4 — legacy /api/find-user-id 帳戶枚舉面

name + phone → 回傳 username 嘅 legacy 端點，速率限制 30/15min。低風險，但配合 F1（需 target username/phone）可收窄攻擊所需資訊。建議退役或強化至 login 同等鎖定策略。

4.「偽測試」風險提示

現有 QA_12persona報告.* 為 persona / UI 流程測試，未發現任何自動化測試斷言：① account-links 唔會提升 tier；② 非 production 重設碼唔回傳；③ bookings/medicalRecords 對象級授權。⚠️ 「測試全綠」唔等於「安全屬性成立」——典型偽測試騙局。建議補上述斷言。
