# 寶天醫館預約系統 — DROS 隱性安全審計報告

- **審計日期**：2026-09-08
- **審計對象**：`booking-aurora`（Express 5 + SQLite + 自製 JWT + Vue 3 CDN）
- **方法論**：DROS（Anti-Stub 空包彈 / GBAI 治理邊界對齊 / Declared≠Implemented≠Verified / 能力混寫 / 偽測試騙局）
- **審計性質**：唯讀源碼審查（無修改、無部署、無滲透）
- **報告原則**：每一項發現都綁定「精確已驗證工件」（file:line 級證據），區分「聲稱 / 實作 / 驗證」三態。

## 0. 一句話總結

治理層基線**明顯高於一般水平**（JWT 撤銷、對象級授權、上傳過濾、靜態攔截都係真貨）。但發現 **1 項 High 級隱性授權缺陷 + 1 項 Medium 級資訊暴露**，核心都係「聲稱與實作自相矛盾」──最經典嘅一處係同一個 function 入面，註解講「account_links 唔影響會員級別」，代碼卻把雙方免費升做付費 `family` 會籍。

## 2. 發現（Findings）

### 🔴 F1 — High：account-links 自助連結 = 免費 family 會籍升級，繞過付費閘門

**DROS 透鏡**：Declared ≠ Implemented（同一 function 自相矛盾）+ GBAI 治理邊界違反（社交關係圖被授予付費特權）。

**聲稱（代碼註解，已驗證）**：
```js
// routes/memberships.js:840
// 與 family_links（家庭訂閱父→子）分開：account_links 係純關係圖，唔影響會員級別／保險。
```

**實作（同一 function，已驗證）**：
```js
// routes/memberships.js:861-862  — 端點只要求 requireAuth（任何已登入用戶）
router.post('/account-links', requireAuth, async (req, res) => {

// routes/memberships.js:896-901  — 目標按 username 或 phone 解析，僅要求 role='customer'、非自己
if (targetUsername) target = await q1("... WHERE username=? COLLATE NOCASE", [...]);
else if (targetPhone) target = await q1("... WHERE phone=?", [...]);
if (target.role !== 'customer') return ...;
if (Number(target.id) === Number(fromId)) return ...;   // 只防連結自己

// routes/memberships.js:923-936  — 「一連即轉」：雙方自動升 family
if (owner && owner.role === 'customer' && owner.membership_tier !== 'family') {
  await run("UPDATE users SET membership_tier='family' WHERE id=?", [ownerId]);   // 928-930
}
if (target.role === 'customer' && target.membership_tier !== 'family') {
  await run("UPDATE users SET membership_tier='family' WHERE id=?", [target.id]);  // 933-935
}
await syncFamilyPlan(headId);   // 943 重算家庭計劃、生成發票（但無向 caller 收費）
```

**漏洞本質**：
1. 任何已登入嘅 `general`（免費）客戶，只要 `POST /api/membership/account-links` 帶 `{ targetUsername: <任意已知客戶> }`，自己同對方都會被升做 `family`。
2. `family` 係付費會籍。`membership_required` 閘門（`routes/bookings.js:317`、`routes/memberships.js:1183-1184`）規定 `general` 非家庭連結用戶只可預約「初體驗」服務；升咗 `family` 就**免費解鎖全部服務預約**。
3. 全程**無 Stripe 付款、無職員確認、無付費閘門**。`syncFamilyPlan` 只係生成家庭發票記錄，唔會阻止 tier 升級或追收費用。
4. 利用面極低：只需要目标用戶嘅 username 或 phone（甚至可經 legacy `/api/find-user-id` 枚舉取得，見 F4）。

**影響**：權限提升（免費付費會籍）+ 營收繞過（付費牆失效）。可自我觸發，無需他人配合。

**為何係「隱性」**：項目記憶（working memory）原記載「account_links = 純關係圖，唔影響等級/保險/訂閱」，與實際代碼直接矛盾。呢個矛盾甚至寫喺相鄰代碼行入面（840 註解 vs 928-935 實作），係最乾淨嘅 DROS 證物。

**修復建議**（按 GBAI 治理還原）：
- 選項 A（最小改動）：刪除 928-936 嘅 tier 升級邏輯，令 account_links 真正只係關係圖；family 會籍只經 Stripe `applyActiveSubscription` 取得。
- 選項 B（若產品真要「連結即升級」）：加 `requireRole('staff','admin')` 或 Stripe 付款確認；並**更新 840 行註解**消除 Declared≠Implemented 矛盾。
- 無論 A/B，補一條測試：斷言「general 用戶自助 account-links 後 tier 維持 general」。

### 🟠 F2 — Medium：重設密碼驗證碼於非 production 經 DEV FALLBACK 回傳客戶端

**DROS 透鏡**：Anti-Stub 環境守衛不完整（條件含「SMTP 未配置」→ 即使 production 部署若漏設 EMAIL_PASS 亦觸發）。

**已驗證工件**：
```js
// routes/auth.js:548-556  （/api/auth/send-reset-code 內）
const isDev = process.env.NODE_ENV !== 'production' || !process.env.EMAIL_PASS;
if (isDev) {
  console.warn(`[DEV FALLBACK] 驗證碼 ${verificationCode} 已生成...`);
  return res.json({ ok: true, ..., dev_fallback: true, verification_code: verificationCode });
}
```

**問題**：當 `NODE_ENV !== 'production'` **或** `!process.env.EMAIL_PASS` 時，6 位重設驗證碼直接寫入 HTTP 響應體。若以下任一情況發生，即洩漏：
- staging / preview 環境 `NODE_ENV=development`（常見）；
- production 部署但 `.env` 漏設 `EMAIL_PASS`（SMTP 未配置，但站點照常運作）。

攻擊者取得驗證碼即可完成密碼重設 → **帳戶接管**。

**修復建議**：`isDev` 只應由 `NODE_ENV !== 'production'` 決定，唔應包含 `!EMAIL_PASS`；且縱使 DEV 模式，驗證碼亦只應寫入 server log，絕不回傳響應體。

### 🟡 F3 — Low：AI 問診路由全公開，無認證

**DROS 透鏡**：能力混寫（本應登入後使用嘅業務能力，對匿名完全開放）+ 治理不一致。

**已驗證工件**（`routes/ai.js`）：
```js
module.exports = (db) => {                                  // :9  無 auth 依賴注入
router.get("/categories", (req, res) => {...});             // :21 無 requireAuth
router.post("/start-consultation", aiWriteLimiter, ...);    // :40 只得頻限
router.post("/submit-answer", aiWriteLimiter, ...);          // :91 只得頻限
router.get("/get-recommendation", (req, res) => {...});      // :188 無 requireAuth
```

四個路由均無 `requireAuth` / `requireRole`。風險低（規則式推薦、唔寫 PII），但：① 若日後接 LLM 後端會有成本/濫用面；② 與「會員才能用 AI 推薦」嘅產品假設不一致。建議至少加 `optionalAuth` 以支援會員個人化，並於文檔聲明此端點公開。

### 🟡 F4 — Low/Info：legacy `/api/find-user-id` 帳戶枚舉面

`routes/users.js` 或 `server.js` 中 `name + phone → 回傳 username` 嘅 legacy 端點，速率限制 30/15min。低風險，但配合 F1（需 target username/phone）可收窄攻擊所需資訊。建議：若已無前端使用，直接退役；否則降至與 login 同等鎖定策略。

## 3. Anti-Stub 正面清單（已驗證「真嘅」控制）

DROS 唔係只搵碴，亦要確認聲稱嘅控制確實實作咗：

- ✅ **JWT 撤銷鏈**：`services/jwt.js` SESSION_SECRET 缺漏時 production 直接退出；`verifyToken` 用 `timingSafeEqual`；jti 撤銷 + `user_revoked`（登出全部裝置）持久化至 SQLite。非 stub。
- ✅ **admin 二次驗證**：`routes/admin.js:19-43` `verifyAdminPassword` 真正查 DB + `verifyPassword` 比對登入密碼，新用戶/改密/刪除/改名等敏感操作均掛載。非 stub（推翻咗「可能係空殼」嘅假設）。
- ✅ **對象級授權**：bookings `isOwnerOrStaff` 覆蓋 GET/PUT/DELETE `/:id`（無 IDOR）；medicalRecords `doctorOwnsTarget` / customer 只睇自己 / admin-staff 含 `hide_from_head` 成人隱私過濾；users `isSelfOrAdmin` + 改密刪除需 `adminPassword`。
- ✅ **上傳安全**：multer diskStorage + MIME 白名單 + 隨機檔名（防路徑注入）+ `..` 拒絕；`/uploads` 靜態只放行圖/片擴展名；`BLOCKED_STATIC` 正則攔截 `.env`/`.db`/`_` 前綴等敏感檔下載。
- ✅ **頻限鏈**：全局 500/15min、login 20/(account+IP)、帳戶鎖定 5 次失敗、驗證碼冷卻 1 分鐘；captcha 測試後門 `CAPTCHA_TEST_BYPASS` 僅非 production 生效（良好實踐）。
- ✅ **XSS**：live 頁無 `v-html` 及 server→innerHTML sink。
- ✅ **註冊開關**：`allow_public_registration` 預設關閉。

## 4.「偽測試」風險提示

現有 `docs/QA_12persona報告.*` 為 persona / UI 流程測試，**未發現任何自動化測試斷言以下安全屬性**：
- account-links 唔會提升 tier（F1 防線）；
- 非 production 環境重設碼唔回傳響應體（F2 防線）；
- bookings / medicalRecords 嘅對象級授權（F-正面上嘅控制）。

⚠️ 呢表示「測試全綠」唔等於「安全屬性成立」——典型偽測試騙局。建議補上述斷言到測試套件，令 DROS 嘅「Verified」真正落地。
