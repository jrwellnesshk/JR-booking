3. 優化建議

3.1 立即修（P0）

  1. 統一 API 欄位命名：建立 OpenAPI，全部 snake_case（對齊 DB）。修 /api/bookings POST 改收 customer_name/service_id/appointment_date/doctor_name，保留 camelCase alias 一個季度。
  2. 修 /api/auth/send-reset-code 500：emailService 失敗時至少回 200 + 把驗證碼寫入 DB，sandbox 環境印驗證碼到 console。
  3. 修 /api/settings/doctors 公開權限：搬去 /api/public/doctors 或 /api/triage/doctors。
  4. 修客人改自己密碼：前端 PUT /api/users/me/password，後端自動用 token 嘅 user.id。
  5. 電話格式寬鬆化：/^[\d\s\-\+\(\)]{6,}$/ 接受國際格式。

4. 功能接駁（API Contract 一致性）

🔴 欄位命名分裂

端點輸入風格例子
/api/auth/login混合username + captchaAnswer
/api/bookings POSTcamelCasecustomerName / serviceId / appointmentDate / doctorName
/api/membership/account-links POSTcamelCasetargetUsername / targetPhone / relation
/api/membership/privacy POST短hide
/api/admin/users POSTsnake_caseusername / name / phone / email / role
/api/users/:id/password PUT混合oldPassword / newPassword

後果：前端與後端緊耦合但 API 冇 contract 文件 → 一改就爆。任何第三方整合（mobile app、外部 CRM）都會撞板。

根治：選 snake_case 為標準（對齊 DB 與現有多數端點），寫 OpenAPI 3.0，加 CI contract test。

5. 安全性

✅ 已做到（17 項全過）

  • 暴力登入限流 8 次 → 429
  • 偽造 JWT → 401
  • SQL 注入 → 404（sqlite 參數化）
  • IDOR 改他人密碼/通知 → 403
  • 員工越權看 admin/批假/刪用戶 → 403
  • 客人看全店病歷/admin 端點 → 403
  • 驗證碼 cooldown 60s
  • 補位醫師=本人 → 400
  • 重複請假 → 409
  • 員工不可建管理員 → 403
  • 2FA（adminPassword 校驗）啟用
  • 密碼分層政策啟用
  • JWT revocation 持久化
  • 密碼重設日誌 / 可疑活動日誌

⚠ 需要加強

  1. send-reset-code 500 暴露內部錯誤（dev 環境） — 生產應隱藏
  2. XSS in feedback 後端接受 <script> — 需驗證輸出端 sanitize
  3. /api/admin 對 customer 返 404 而非 403 — 輕微 enumeration 風險
  4. 公開 CAPTCHA 端點 — 需確認隨機足夠
  5. CORS 設定 — 未在測試中驗證跨域
  6. JWT 過期時間 — 未驗證 access token 過期策略
  7. HTTPS / Secure cookie — 部署層面（ALB + ACM）
  8. Rate limit 全站 — 只 login/email 有，其他端點缺
